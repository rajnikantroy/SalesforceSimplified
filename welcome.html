🚀 Getting Started

Salesforce Simplified operates in two convenient modes tailored to your workflow:

  1. Injected Floating Overlay (In-Page Mode)

    When browsing any Salesforce page (Lightning, Setup, Visualforce, or My-Domain), a subtle launcher icon appears in the bottom corner. Hover over or click the launcher icon to open the sliding side panel without losing your context.

  2. Full-Page Standalone Tab (Workspace Mode)

    Click the extension icon in your Chrome toolbar or press Alt + Shift + S. The standalone tab (simplified.html) works independently of any active tab, allowing you to manage multiple org connections, run deep searches, and switch contexts effortlessly.

  3. Seamless Authentication

    The extension automatically uses your active Salesforce browser session cookie. If your org hides browser sessions or enforces high-assurance policies, choose from one of three built-in sign-in options (OAuth 2.0, Custom Connected App, or Session ID).

⚡ Dynamic Org Describe & Dual-View Engine

Unlike traditional tools that rely on static hardcoded lists, Salesforce Simplified connects directly to your org's REST & Tooling APIs to inspect its live schema in real-time.

🔍 Live Dynamic Describe

Discovers standard SObjects, custom objects (__c), custom metadata types (__mdt), external objects (__x), and installed managed package components instantly.

👥 Dual Perspective

Toggle seamlessly between My Items (components created or modified by you) and All Items across the entire organization.

⚡ Optimized Pagination

Fetches up to 200 records per batch ordered by recency (e.g. LastModifiedDate or StartTime), delivering blazingly fast response times even in massive enterprise orgs.

Pagination & Search Strategy: When working with component types that exceed 200 items (such as Apex classes or custom fields in mature orgs), Select All acts on the 200 items currently on screen. For building manifests across large component types, use the Quick Find search input first to filter down to the exact items you require.

📦 Package.xml Manifest Builder & One-Click Retrieve

Construct precise, deployment-ready package.xml manifests and retrieve complete source ZIP archives directly from your browser.

🔗 Related Components Auto-Expansion

Ticking a SObject automatically resolves and includes its child Custom Fields, Layouts, Record Types, Validation Rules, Buttons, Compact Layouts, and List Views. Profiles and Permission Sets bring in all granted permissions.

🧠 Dependency API Reference Scanner

Uses Salesforce's Tooling Dependency API to analyze Apex classes, Visualforce pages, Aura/LWC bundles, and Flows to discover and offer missing referenced fields, classes, and SObjects.

🛡️ Managed Package Purging (04t Guard)

Identifies components installed from managed packages that cannot be retrieved, alerting you and offering a 1-click option to purge them so your retrieve request succeeds.

⚡ Browser-Native Retrieve ZIP

Click Retrieve to request the org to package the metadata. The org builds the zip file with native -meta.xml definitions, ready for deployment via sf project deploy or Ant — or use Send to another org to deploy the same selection straight into a paired org, no zip involved.

Reference Scanning Note: The reference scanner relies on Salesforce API dependency graphs. Note that dynamic references (such as string-concatenated SOQL queries or Schema.getGlobalDescribe() string lookups) cannot be detected via static analysis.

📊 SObject Data Export Engine

Export record data from any standard or custom SObject directly into formatted JSON files for backup, migration, or analysis.

Full Schema Querying Unlike basic table dumps that only save visible screen columns, the export engine re-queries Salesforce to retrieve every available field value on the selected SObjects.
Multi-Object Support Select records across multiple different SObjects in a single session; each object is queried independently and bundled cleanly.
Fallback Safeguard If an org restricts query access to certain system fields, the engine gracefully falls back to exporting all screen-rendered grid columns rather than failing.

🧩 On-Page Tools: All Fields & List Export

Two buttons that appear on the Salesforce page itself rather than in the side panel — one on record pages, one on list views. Both sit beside the standard action buttons and open a full-screen workspace.

🗂️ All Fields (record pages)

Opens every field on the record — not only the ones the page layout happens to show — with its current value in an editable two-column grid. Save writes back only the fields you actually changed. Fields your profile cannot edit, and fields Salesforce itself never allows writing, are shown read-only rather than failing at save time. A copy icon puts the whole record on your clipboard as JSON.

📤 Export (list views)

Opens the list's underlying SOQL in an editable box so you can widen, filter, or re-order it before running. Results land in a full-screen grid with column headers and a filter box, and download as JSON, CSV, or Excel. Field-name suggestions appear as you type, and a query the data API rejects is retried automatically against the Tooling API.

Where They Appear Record detail pages and list views, in both Lightning and Classic. The buttons are placed beside the standard action bar, never inside it, so Salesforce's own components are left untouched.
Every Object Standard and custom alike — the object and record are read from the page URL, so nothing needs configuring per object.
Permission Aware Edit access is checked against the record before the grid becomes editable, and a save the org refuses is reported with Salesforce's own validation message in full, not a truncated one.
Turn Them Off Both buttons have their own switch under System Settings → On Salesforce pages if you would rather keep the page exactly as Salesforce ships it.
Both tools need an authenticated session for the org you are viewing. If you are signed out, clicking either one opens the usual sign-in card instead of failing silently.

🕸️ Event Graph: What Actually Happened

Something ran, and the record looks wrong. The Event Graph gathers what the org can tell you about a transaction — audit trail entries, debug logs, related records — and draws the relationships between them, so the question stops being “which log do I open” and becomes “what touched this, and in what order”.

🔗 Correlated, with its confidence stated

Every relationship it draws carries how it knows: a link read directly off a record is confirmed, one inferred from timing is not, and the two are never presented as though they were the same. A graph that guesses silently is worse than no graph.

🕳️ Honest about what it could not see

Most orgs have no debug log for the transaction being investigated, Event Monitoring is a paid add-on, and SetupAuditTrail needs “View Setup and Configuration”. Each of those is a normal outcome, not an error — it contributes an acknowledged gap in the picture rather than a failed load.

▶️ Replay does not re-run anything

Replay walks back through a recording. It makes no callout, touches no record and starts no flow — worth saying plainly, because “replay” in a Salesforce context can reasonably be read as “run it again”, and running a payment twice to find out why it failed once is not a debugging technique.

📖 Every request is a read

The engine itself is plain JavaScript with no network access at all; only the query layer talks to Salesforce, and only ever to read. Nothing here writes to your org.

🔀 Org Sync: Moving Work Between Two Orgs

Pair two orgs you are signed in to, then send components or records from one to the other — without leaving the browser, and without a zip going anywhere near your downloads folder. Every job is staged for review first; nothing reaches the second org until you apply it.

📦 Metadata, retrieve to deploy

Tick components in any list — the same selection package.xml is built from — and send them down a pipeline. The source org retrieves, the target deploys, and the deploy always rolls back on error, so a package that fails part-way leaves the target as it was. Validate only runs the same deploy check-only.

⚡ Quick deploy

A successful validation is held by the org for ten days. Deploying it needs no retrieve, no recompile, and no second test run. Offered only on validations the org will actually accept — one that ran no tests is not eligible, and the row says so rather than leaving you a button that fails.

🗃️ Records, matched on a key you choose

Record Ids differ between orgs, so you nominate the field that means the same row in both. External Id fields are upserted by the org itself; any other filterable field is looked up in the target, with matches updated and the rest created. There is also a mode that matches nothing and creates everything.

📋 Jobs, with history that survives

Staged, succeeded and failed jobs are kept per pipeline, grouped by attempt, and paged. Failures carry the org's own words — the component and line, or the record and the field — plus the reason when the cause was this extension rather than the org.

Never Unattended A job is created by you and runs when you apply it. Nothing is deployed on a schedule, in the background, or as a side effect of an edit. The button says what it will do: Deploy, Validate or Migrate.
Survives the Browser A deploy takes minutes; Chrome stops the extension's worker after seconds. The job records the org's deploy id, so a job interrupted mid-deploy is picked back up and reported rather than reading as failed while it actually succeeded.
Open It As a Page The in-page panel acts as the org whose page it is on and cannot be pointed anywhere else — signing in to a second org from the panel does not move it. Simplified's own page (the ↗ button) has an org picker, so it can send from either end of any pipeline. The panel says so when none of your pipelines can run from where it is.
Two Live Sessions Both ends need a session in this browser. Orgs you have used are listed with a Signed in or Expired tag, and an expired one offers to open that org so you can sign in again — Salesforce takes your credentials, never this extension.
What Is Not Carried Lookup fields hold Ids belonging to the source org and are left behind. A record whose key matches more than one record in the target stops the job rather than guessing which one you meant.
Records are written all or none, up to 200 per job. That is the largest single all-or-nothing write the org accepts — larger migrations are more than one job, on purpose.

📤 Send what is in hand, from anywhere

The footer already carried the counts; it now carries the two acts that go with them. Deploy (n) appears when components are ticked and Migrate (n) when records are, each opening this page with the selection. They open the page rather than staging on the spot: staging needs a pipeline, and picking one from a footer button would be choosing which org to write into on your behalf.

👀 Review shows what it is asking about

The review dialog lists what the job actually carries — every component, or the object, the matching key and the full SOQL — with the decision pinned in a footer that a long list cannot scroll away from. The button names the act: Deploy, Validate or Migrate.

🩺 Errors, Sessions and Dependencies

Most of what goes wrong between two orgs goes wrong for a reason you cannot see from the message. This is about making those reasons visible, and about not reporting the ones that were never a problem.

🧭 Every error has a code

Messages carry a code such as SS-101, linked to the error reference — what causes it, and the steps to resolve it. Failed jobs carry their code too, so a failure from last week can still be looked up.

😴 Fewer errors that were never errors

Chrome stops an extension's background worker after about thirty seconds idle. A message arriving while it restarts used to surface as a failure on a page where nothing had been attempted. It is now sent once more instead. Only lost messages are retried — never one the worker already acted on.

🔑 The right org's session

Salesforce sets a session cookie on login.salesforce.com as well as on each org's own host, and a parent-domain cookie matches every org beneath it. Picking the wrong one made an org reject a session that looked perfectly valid — reported as “expired” to someone who had just signed in. The org's own cookie is now preferred.

🔗 Named Credentials pull their services

External Services point at a Named Credential, so no forward dependency scan could ever reach them — the credential deployed and its services were left behind. package.xml now asks the reverse question for credentials, and finds the linking field from the org's own describe rather than a name written into this extension.

An error code is stable; the sentence beside it may be reworded. Quote the code in a bug report and it will still mean the same thing. The reference is also reachable from About → Help and feedback.

🔑 Authentication & Connection Modes

Salesforce Simplified seamlessly piggybacks on your existing browser session. If session cookies are restricted by your org, three robust authentication methods are supported:

Authentication Method How It Works Best Suited For
Sign in with Salesforce Standard OAuth 2.0 Web Server Flow using the extension's default packaged OAuth app. Select This Org, Production, Sandbox, or a Custom Domain URL. Standard Salesforce orgs allowing default extension authentication.
Custom Connected App Use your organization's own internal Connected App. Enter your Consumer Key — the panel provides the exact OAuth Redirect URI to register in Setup. Enterprise orgs requiring strict app whitelisting and internal OAuth policies.
Direct Session ID (sid) Paste an active session token. Held strictly in volatile RAM memory for the browser session — never written to disk or local storage. Restricted orgs without Setup administration access.
Session ID Extraction Tip: Obtain your session ID via Developer Console → Debug → Open Execute Anonymous Window by executing: System.debug(UserInfo.getSessionId());
Alternatively, copy the sid cookie from your my.salesforce.com domain. Note: sid tokens from lightning.force.com origins are scoped to UI rendering and will be rejected by Salesforce APIs.

🔐 One grant per org, not one in total

Signing in to a second org used to replace the first: come back to it and the grant was simply gone, with nothing to say why. Tokens are now kept per org, so several can be authorised at once — which is what a pipeline needs, since a pipeline is two orgs by definition. Refreshing one leaves the others alone, and signing out of one signs you out of one.

🗂️ Orgs in this browser

Every org you have used is listed on Org Sync & Jobs, tagged Signed in or Expired. The list outlives the sessions, so an org whose session has gone still says so rather than looking like one that works. An expired row offers to open that org — Salesforce takes your credentials, never this extension, which holds no password and asks for none.

🍪 The right org's cookie

Salesforce sets a session cookie on login.salesforce.com as well as on each org's own host, and a parent-domain cookie matches every org beneath it. Picking the wrong one made an org reject a session that looked perfectly valid. The org's own cookie now wins, and when only a borrowed one exists the message says where it came from.

🔔 It asks rather than sitting silent

On a first visit the panel waited on a startup promise that could never settle — so it assumed a session it did not have, and offered no sign-in and no error. It now starts either way: with nothing to read, the sign-in card appears.

🏢 Multi-Org Management

Manage and switch between multiple Salesforce environments (Production, Sandbox, Scratch Orgs, and Developer Edition orgs) effortlessly from a single window.

Open the Standalone Full Page (simplified.html) and select any connected org from the top dropdown menu. Switching orgs automatically reloads the workspace to present that specific org's schema, audit history, and recent items.

🔒 Security, Privacy & Data Protection

100% Client-Side Local Execution: Salesforce Simplified operates entirely inside your local browser. There are no intermediate third-party servers, analytics trackers, or external endpoints. All API calls travel directly between your browser and official Salesforce infrastructure (*.salesforce.com, *.force.com).
Session Protection Session tokens are strictly memory-resident for the active session. Pasted Session IDs are never written to disk or browser storage.
Strict Origin Scoping The background service worker enforces strict origin checks in code, refusing to send session headers to non-Salesforce endpoints.
Read-Only Operations The extension operates in read-only mode for metadata and records, ensuring zero risk of accidental org mutations.

❓ Frequently Asked Questions (FAQ)

Q: Why are some panels or setup audit trails showing empty results?

Certain administrative endpoints require the View Setup and Configuration administrative permission. If your user profile lacks this permission, those specific sections will display a graceful warning while the rest of the extension remains fully operational.

Q: Why does Session ID authentication fail with an API error?

Ensure your session ID was obtained from a my.salesforce.com origin (or via Developer Console). Session IDs originating from lightning.force.com UI pages are restricted by Salesforce security and cannot be used for API access.

Q: Why does a metadata list only show 200 items when my org has thousands?

To prevent browser memory bloat and API quota exhaustion, Salesforce Simplified fetches metadata in recency-ordered batches of 200 items. To access specific items beyond the top 200, use the Quick Find search input to filter the org query.

Q: Can I use Salesforce Simplified across multiple org tabs simultaneously?

Yes! Each tab automatically resolves its corresponding org context and session token independently.
